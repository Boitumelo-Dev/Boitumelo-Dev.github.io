Greedy was fast but blind. Dynamic programming is the opposite bargain: it looks at every alternative, so it's always right — and it stays fast by remembering every sub-answer instead of recomputing it. Below is naïve recursion computing a Fibonacci number. Watch how much work it throws away.

See the waste ↓
01 The waste, and the fix

One idea: stop recomputing

To find fib(n), naïve recursion re-derives the same small answers over and over. Each coral node below is a sub-answer we already worked out elsewhere — pure wasted effort. Flip on memoisation and the whole tree collapses.

Fibonacci recursion tree interactive

Every node is a function call. Teal = solved once. Coral = a repeat of work already done. Violet = a cache hit (memoisation returns instantly, no expansion).

↖ Slide n up and watch the naïve count explode while the memoised count barely moves. That gap is dynamic programming.

Two conditions have to hold for this trick to work, and they're the entire theory of DP. The first you already met with greedy. The second is new and is the reason DP exists at all.

🧩

Optimal substructure

The problem breaks into subproblems whose optimal answers combine into the whole. fib(n) = fib(n−1) + fib(n−2). Greedy needs this too — it's the shared foundation.

♻️

Overlapping subproblems

The subproblems repeat. fib(50) needs fib(49) and fib(48) — but fib(49) also needs fib(48). Solve it once, reuse it forever.

Substructure without overlap? Then you don't need DP — plain recursion is enough. Merge sort has optimal substructure (sort halves, merge) but its halves never repeat, so there's nothing to cache. DP only earns its keep when subproblems overlap.
02 Two ways to remember

Top-down and bottom-up

Once you know subproblems overlap, there are exactly two ways to avoid the waste — and they meet in the middle.

Top-down — keep the recursion, add a memo

Write the natural recursive definition, but the first time you compute an answer, cache it. Every later request is an instant lookup. It trades memory for compute and only ever solves subproblems it actually needs.

top-down · memoised · O(n)

Bottom-up — fill from the smallest up

Turn the recursion inside out: solve the smallest subproblems first, so by the time you need a bigger one its pieces are already sitting there. No recursion, and for Fibonacci you don't even need a full table — just a two-value sliding window. Step through it:

Bottom-up fill interactive

Each new cell is the sum of the previous two. The window you actually keep in memory is just a and b — everything behind it can be forgotten.

bottom-up · O(n) time · O(1) memory

Top-down

  • Natural translation from the recursive form
  • Only computes subproblems it actually needs
  • Slower when many subproblems are revisited (call overhead)
  • Needs a full memo table in memory

Bottom-up

  • Faster when many subproblems are revisited
  • Often uses far less memory (or none)
  • Less intuitive than the recursion
  • Must compute every subproblem, needed or not

Rule of thumb: prototype top-down (it mirrors how you think), then rewrite bottom-up if memory gets tight.

03 Fixing greedy's failure

Making change, done right

Remember the coin set {1,2,5,10,20,25} making 42? Greedy grabbed 25 first and locked itself into 4 coins. The true answer is 3 coins. DP finds it — by refusing to commit early and instead considering every alternative.

The optimal-substructure insight: the best solution for 42 either uses a 25 or it doesn't. If it does, the rest is 1 + best(42−25). If it doesn't, it's just the best using the smaller coins. Take the minimum. Written as a recurrence over "first i coins, amount j":

c[i, j] = min(  c[i−1, j]  // skip coin i ,   1 + c[i, j − dᵢ]  // use coin i )
Coin DP table interactive

Each cell holds the fewest coins to make that amount. We fill left→right; every cell just looks back a few steps and takes the best. Click the target cell to see how it decided.

DP escapes the trap greedy fell into precisely because it never locks in a locally tempting choice. It lays out the cost of every path and reads off the minimum — the cache is what keeps that exhaustive search affordable.

04 Three properties, one graph

Seeing the properties on a shortest path

A single weighted graph shows all three ideas at once. We want the cheapest route from A to G. Flip between the lenses.

Greedy fails: at C the locally cheapest exit is the edge weighted 2, but it dead-ends into a 40, so the greedy choice is not on the optimal path. Overlapping: both A→G and B→G pass through C→F, so you compute that once (cost 17) and reuse it. Substructure ✓ and overlap ✓ but greedy ✗ — this is a textbook DP problem.

05 When the order is the answer

Matrix-chain multiplication

Multiplying a chain of matrices always gives the same result — but the order you bracket them changes how much arithmetic it takes. Sometimes by a lot.

Multiplying a p×q by a q×r costs p·q·r scalar multiplications. So for three matrices, where you put the brackets decides everything:

Parenthesisation cost interactive

Same three matrices, two bracketings. Pick one and watch the arithmetic.

72(M₁M₂)M₃
160M₁(M₂M₃)

Two orderings, and one does more than double the work of the other. With n matrices the number of bracketings explodes, but the subproblems overlap heavily, so DP nails it. Define m(i,j) as the cheapest way to multiply Mᵢ…Mⱼ and try every split point k:

m(i, j) = mini ≤ k < j { m(i, k) + m(k+1, j) + di−1·dk·dj }
top-down · memoised over (i, j)

The whole lecture, distilled

  • DP rests on optimal substructure (break into subproblems) plus overlapping subproblems (those pieces repeat). Overlap is what greedy and merge sort lack.
  • The move is always the same: solve each subproblem once, store the answer, reuse it — trading memory for a huge cut in compute (Fibonacci: O(2ⁿ) → O(n)).
  • Top-down keeps the recursion and memoises on the fly; bottom-up fills from smallest to largest and can shed most of the memory.
  • Where greedy commits early and loses (making change for 42), DP considers every alternative and is always optimal.
  • Recipe: write a top-down recursion, spot which subproblems repeat, decide how to store them — and if memory bites, flip to bottom-up.
Greedy gambles. Dynamic programming remembers.
