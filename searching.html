03 — Linear search · mechanism

Walk the array until you find it (or run off the end)

Start at index 0. If the cell holds the key, stop. Otherwise step right and repeat. If you pass the last index, the key isn't there — return −1. No assumptions about order needed.

What to notice: the amber cursor only ever moves right, and cells behind it turn rose — permanently ruled out. The loop's exit is either a match or falling off the end.

04 — Linear search · completeness

It always returns the right answer (Theorem 1, by induction)

Completeness asks: will it find a solution if one exists? The notes prove yes for any length by induction. The idea is visual — a length-k array is a length-k−1 array (handled by the hypothesis) plus one new final cell.

What to notice: if the key sits anywhere in the first k−1 cells (teal), the induction hypothesis already guarantees a correct result. Only the last cell (indigo) is genuinely new — and the two cases there (match / off-the-end) both return correctly. That closes the proof.

Proof shape · induction on length n
Base (n=1): either key = myList[0] → return 0, or not → loop increments past the end → return −1. Both correct.
Hypothesis: correct for length k−1.
Step (n=k): key in positions 0…k−2 is covered by the hypothesis; the only new case is position k−1 (match → return k−1) or absent (return −1). ∎
05 — Linear search · optimality

You can't beat n comparisons on an unordered array — the adversary proof

Optimality compares an algorithm to the problem's floor. For an unordered array we prove that floor is n comparisons using an adversary: whatever cells you check, the key hides in one you haven't. You be the algorithm — click cells to check them.

Values are hidden. Click a cell to "check" it — the adversary answers.

Cells checked: 0. The key could still be in any unchecked cell.

What to notice: after n−1 checks there's still one unseen cell — and the adversary is free to have put the key there. So you must check that last cell too. Any correct algorithm needs all n comparisons in its worst case.

Aha · why this makes linear optimal
The lower bound for the problem is L(n) = n. Linear search does at most n comparisons. Its worst case matches the floor — so it is Θ(n) and optimal for unordered arrays. "Hide the key in the last place it looks" is the whole argument.
06 — Linear search · time complexity

Best O(1), worst O(n), and an average that depends on q

Best case: the key sits at index 0 — one comparison, done. Worst case: the key is absent — every one of the n cells is compared. The average is the interesting one.

Best & worst case
best: key at index 0 → g(n)=1 → O(1)   ·   worst: key absent → g(n)=n → O(n)

The result is gA(n) = q(n+1)/2 + (1−q)n. Drag both and watch where the average lands between "instant" and "worst case".

gA(n) = q(n+1)/2 + (1−q)n (n+1)/2, q=1 n, q=0

What to notice: at q=1 (key certainly present) the average is (n+1)/2 — about half the list. At q=0 (certainly absent) it collapses onto the worst case n. Either way it's linear in n, so the average case is still O(n).

Why O(n) · the limit proof
limₙ→∞ [q(n+1)/2 + (1−q)n] / n = (2 − q)/2
For any q ∈ [0,1] this is a finite positive constant, so gA(n) = O(n). (Notice c depends on q.)
07 — Linear search · space complexity

O(n): the array dominates, everything else is a constant

Linear search stores the length-n array plus a couple of scalar variables (the index). The scalars don't grow with the input, so total memory is O(n) — driven entirely by the array itself.

Space
n array cells + O(1) bookkeeping = O(n), regardless of input.
This is the same for both algorithms in these notes — the interesting differences are all in time.
08 — Bisection search · mechanism

Halve the problem every comparison — but only if it's sorted

Keep a window [low, high]. Look at its middle. Equal? Done. Key smaller? The answer must be in the left half — discard the right. Key larger? Discard the left. Each comparison throws away half the array. This is decrease-and-conquer.

What to notice: the teal window shrinks by half after every amber probe; the discarded half dims to rose. Reaching a single-cell window and missing means the key isn't there → −1.

Gotcha · sorting is not optional
Bisection's whole logic — "smaller ⇒ go left" — relies on order. On an unsorted array a comparison tells you nothing about which half to keep, so discarding a half can throw away the key. That's the price of admission: bisection needs a sorted list; linear does not.
09 — Bisection search · completeness

It always terminates with the right answer (Theorem 6)

Two things must hold: it always stops, and when it stops the answer is right. Both come from the window strictly shrinking.

Why it terminates & is correct
Every iteration either finds the key or moves low up / high down past mid, so the window [low, high] strictly shrinks. It can't shrink forever — eventually either the key is found, or low > high and the loop halts returning −1. Because the list is sorted, whenever the key exists the discarded half provably can't contain it, so a present key is never skipped. ∎
Aha · base case n=1
A one-cell window: either myList[0] = key (found → return 0) or not (one branch sets low>high, loop halts → return −1). The smallest case already shows the two exits that the general proof relies on.
10 — Bisection search · optimality

⌊log₂n⌋ + 1 comparisons is the floor — the decision-tree argument

Any search on a sorted list is a sequence of index checks, and each check sends you left or right. That makes every such algorithm a binary tree of indices. The worst-case number of comparisons is the longest root-to-leaf path: the tree's height plus one.

What to notice: bisection's tree is balanced — height ⌊log₂n⌋, so ⌊log₂n⌋+1 comparisons worst case. Linear search is the same idea gone wrong: its tree is a single chain of height n−1, needing n comparisons. Balance is everything.

Why a balanced tree can't be shorter — Proposition 1

A binary tree with N nodes has height h ≥ ⌊log₂N⌋. The reason: level i holds at most 2ⁱ nodes, so a tree of height h holds at most 2ʰ⁺¹ − 1. To fit N nodes you need enough levels.

What to notice: pack nodes as tightly as possible (a balanced tree) and the height still can't dip below ⌊log₂N⌋. Since every list index needs its own node (N ≥ n for a complete algorithm), the height — and so the worst-case comparisons — is bounded below by ⌊log₂n⌋ + 1.

Aha · the chain that closes it
worst-case comparisons = height + 1 ≥ ⌊log₂N⌋ + 1 ≥ ⌊log₂n⌋ + 1. Bisection achieves exactly ⌊log₂n⌋ + 1 (next section), so it hits the floor — optimal among all sorted-list search algorithms.
11 — Bisection search · time complexity

Best O(1), worst O(log₂ n)

Best case: the key is exactly the first middle you check — one comparison. Worst case: you keep halving until a single cell remains. Let's build the worst-case count from its recurrence.

Note on the notes
Theorem 7 in the notes is labelled "O(1) in the worst case" — that's a typo. The single-comparison result is the best case (key at the first mid). The worst case is what we derive next.

Unroll the recurrence

One comparison, then recurse on a half of size ⌊n/2⌋. Slide n and watch it collapse to a single cell — the number of halvings plus one is the comparison count.

Prove the closed form by induction

Why O(log₂n) · Theorem 8
gW(n) = ⌊log₂n⌋ + 1  ≤  a·log₂n  ⟺  1 + 1/log₂n ≤ a
As n → ∞, the 1/log₂n term vanishes, so any a > 1 works ⇒ gW(n) = O(log₂n).

Aha · optimality is relative to assumptions
Both algorithms are optimal — for different problems. Linear matches the floor L(n)=n when nothing is known about order; bisection matches L(n)=log₂n when the list is sorted. Sorting doesn't make linear "wrong" — it changes the problem, and with it, the floor.
13 — Decision guide

Which one, when?

Unsorted data

Use linear

No ordering to exploit, and linear is provably optimal here. Sorting first only pays off if you'll search repeatedly.

Sorted, many searches

Use bisection

O(log n) per query crushes O(n) as n grows. Amortise the one-time sort across all the lookups.

Sorted, one search

It depends

If already sorted, bisection. If you'd have to sort just for one lookup, a single linear pass may be cheaper.
